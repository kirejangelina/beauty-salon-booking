# Риски проекта

Здесь описано, что может пойти не так при разработке и работе системы Beauty Booking и что мы делаем, чтобы этого избежать или уменьшить ущерб.

Каждый риск помечен статусом:
- **[реализовано в прототипе]** — митигация уже есть в текущем коде;
- **[в планах]** — митигация описана как целевая, в прототипе пока не реализована;
- **[сознательно принимаем]** — риск известен, решение отложено осознанно.

---

## Главный риск

### Двойная запись

**Что может случиться.** Два клиента одновременно выбирают одно и то же время у одного мастера. Каждый запрос по отдельности проходит проверку «время свободно», и в итоге в системе оказываются две записи на один слот.

**Почему это важно.** Это ровно та проблема, ради решения которой делается система. Если она не решена, система не выполняет свою задачу.

**Что делаем.**
- **[реализовано в прототипе]** Проверка пересечения интервалов и сохранение записи выполняются в одной критической секции под `asyncio.Lock` в `booking.py`: в каждый момент времени в этом участке находится только один запрос. При конфликте возвращается `409 Conflict`.
- **[в планах]** Проверять пересечение времени внутри транзакции в базе данных.
- **[в планах]** Добавить ограничение на уровне БД, чтобы она физически не позволила сохранить две пересекающиеся записи у одного мастера.
- **[в планах]** Написать тест, в котором два запроса на один слот отправляются одновременно. Должен пройти только один.

Ограничение текущего решения: `asyncio.Lock` работает только в пределах одного процесса. При запуске нескольких экземпляров `booking-service` защита от гонок не гарантируется — это закрывается только переходом на БД с транзакциями.

## Технические риски

### Не работает catalog-service

**Что может случиться.** Когда клиент создаёт запись, booking-service запрашивает у каталога длительность услуги и график мастера. Если каталог недоступен, запись создать не получится.

**Что делаем.**
- **[реализовано в прототипе]** Каталог услуг и мастеров задан статически внутри `booking.py`, поэтому отдельный `catalog-service` в прототипе не требуется и его недоступность на создание записи не влияет.
- **[в планах]** Когда каталог будет вынесен в отдельный сервис — задать таймауты, чтобы запрос не зависал, и возвращать понятную ошибку вместо падения. Добавить проверку `/health` и автоматический перезапуск контейнеров. Ошибки писать в лог.

### Не работает notification-service

**Что может случиться.** Уведомления не отправляются.

**Что делаем.**
- **[реализовано в прототипе]** Запись создаётся независимо от уведомлений. Вызов `POST /notify` выполняется с таймаутом (`NOTIFICATION_TIMEOUT = 5.0`), ошибки `httpx.HTTPError` перехватываются и логируются, но не прерывают создание записи. Клиент получает `201 Created` даже при недоступном `notification-service`.
- **[в планах]** Надёжная доставка с повторными попытками через брокер сообщений.

Этот риск **[сознательно принимаем]**: потеря уведомления при сбое не ломает основной бизнес-процесс, а надёжная доставка появится в следующих версиях.

### Данные в сервисах расходятся

**Что может случиться.** Администратор изменил цену или удалил услугу, а в записях осталась старая информация, или записи ссылаются на несуществующую услугу.

**Что делаем.**
- **[реализовано в прототипе]** Цена и длительность копируются в запись в момент создания, поэтому изменения каталога на старые записи не влияют.
- **[в планах]** Услуги и мастеров не удалять, а отключать; проверять актуальность услуги/мастера через `catalog-service`.

### Путаница со временем

**Что может случиться.** Из-за часовых поясов и перехода на летнее время слоты сдвигаются или показываются неверно.

**Что делаем.**
- **[в планах]** Хранить все даты в UTC, показывать в часовом поясе салона. Проверять работу на границах суток.
- **[реализовано в прототипе]** Валидация времени (`validate_time`) отсекает запись в прошлое и ограничивает горизонт записи (`BOOKING_HORIZON_DAYS = 30`), но полноценной работы с часовыми поясами пока нет.

### Потеря данных

**Что может случиться.** Процесс сервиса упал или перезапустился, данные пропали.

**Что делаем.**
- **[в планах]** Хранение данных в СУБД (например, PostgreSQL) у каждого сервиса; docker volumes, чтобы данные переживали перезапуск; резервное копирование (описать в README).
- **[реализовано в прототипе]** Данные хранятся в памяти процесса `booking.py` и теряются при перезапуске — это осознанное ограничение учебного прототипа (см. README, раздел «Ограничения прототипа»).

### Слишком сложная архитектура

**Что может случиться.** Сервисов слишком много, они плохо согласованы, и в итоге ничего не работает.

**Что делаем.**
- **[реализовано в прототипе]** В MVP остаётся небольшое число сервисов — два реализованных (`booking-service`, `notification-service`) и три спроектированных (`api-gateway`, `user-service`, `catalog-service`). Общение — обычными REST-запросами.
- **[в планах]** Брокер сообщений и прочее добавлять только если MVP уже готов.

## Риски безопасности

### Доступ к чужим данным

**Что может случиться.** Клиент подставляет в запрос чужой id и видит или отменяет чужую запись.

**Что делаем.**
- **[в планах]** На сервере проверять, что запись принадлежит именно этому пользователю. Роль проверять на каждом защищённом запросе. Писать тесты на доступ: клиент не должен видеть чужие записи, а не администратор не должен видеть отчёты.
- **[реализовано в прототипе]** Авторизации нет: административные эндпоинты (`/admin/...`) доступны без проверки прав, CORS разрешён для всех источников (`allow_origins=["*"]`). Это ограничение зафиксировано в README.

### Утечка персональных данных

**Что может случиться.** Имена, телефоны и email клиентов попадают к посторонним.

**Что делаем.**
- **[в планах]** Хранить только необходимое. Пароли хэшировать (bcrypt). Персональные данные не писать в логи. Токены доступа — с ограниченным временем жизни.
- **[реализовано в прототипе]** Хранятся только имя, телефон и комментарий клиента, необходимые для записи; паролей и токенов в прототипе нет.

### Пароли и ключи в репозитории

**Что может случиться.** Пароли от базы данных или секретный ключ для токенов случайно попадают в публичный репозиторий.

**Что делаем.**
- **[в планах]** Файл `.env` добавлять в `.gitignore`. В репозитории держать только `.env.example` с пустыми или тестовыми значениями. Перед каждым коммитом проверять, что секретов в нём нет.
- **[реализовано в прототипе]** Секретов и внешних учётных данных в коде нет, поэтому риск пока неактуален.

## Бизнес-риски

### Клиенты не приходят

**Что может случиться.** Клиент записался и не явился, мастер простаивает, салон теряет деньги.

**Что делаем.**
- **[в планах]** Ввести учёт неявок (статус `NO_SHOW`), ограничить отмену (не позже чем за 2 часа) и число активных записей у одного клиента. В следующих версиях — напоминания и блокировка тех, кто часто не приходит.
- **[реализовано в прототипе]** Статусы визита не ведутся; отмена доступна мастеру/администратору без проверки оставшегося времени (см. README, раздел «Бизнес-правила»).

### График мастера изменился при существующих записях

**Что может случиться.** Мастер заболел или уходит в отпуск, а на эти дни уже есть записи клиентов.

**Что делаем.**
- **[в планах]** При добавлении недоступности система предупреждает администратора о попавших под неё записях. Администратор может перенести или отменить такие записи вручную.
- **[реализовано в прототипе]** График мастера задан статически; управления недоступностями нет.

## Проектные риски (управление разработкой)

### ИИ-агент генерирует неоптимальный или небезопасный код

**Что может случиться.** Агент пропускает бизнес-правила, придумывает лишние эндпоинты, оставляет пароли прямо в коде или не валидирует входные данные.

**Что делаем.**
- **[реализовано в прототипе]** Код проверен вручную: запуск обоих сервисов, прогон сценариев через curl и веб-интерфейс, сверка фактического поведения с документацией. Расхождения между целевой моделью и реализацией явно помечены в README как «в планах». Подробнее — раздел «Использование ИИ-агента при разработке» в README.
- **[в планах]** Передавать агенту README как контекст и не просить сделать всё сразу (работать по одному сервису). Проводить код-ревью сгенерированного кода, проверять валидацию данных. Все настройки выносить в переменные окружения. Писать тесты на ключевые правила.

### Срыв сроков разработки (MVP не готов вовремя)

**Что может случиться.** Срок сдачи подходит, а минимальная рабочая версия не готова.

**Что делаем.**
- **[реализовано в прототипе]** Приоритизация применена на практике: в прототип вошли только обязательные сценарии (создание записи, проверка занятости, отмена, уведомление), а остальное (статусы, каталог как сервис, авторизация) вынесено в README в раздел «Дальнейшие шаги (Roadmap)».
- **[в планах]** Формализовать приоритизацию по MoSCoW в отдельном документе требований.

### Проблемы с развертыванием (Environment Issues)

**Что может случиться.** Система не запускается из-за разницы в окружениях (версии библиотек, ОС).

**Что делаем.**
- **[реализовано в прототипе]** Зависимости зафиксированы в `requirements.txt`; в README описаны шаги создания виртуального окружения и запуска для Linux/macOS и Windows (PowerShell и cmd).
- **[в планах]** Изолировать окружение с помощью Docker; запуск через `docker compose up`; в репозитории — `.env.example` и пошаговая инструкция. Перед релизом проверять запуск на чистой копии репозитория.
